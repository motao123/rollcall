三、Blocker：自动快照必然导致进程崩溃
--------------------------------------------------------------------------------
文件：internal/store/store.go  Save()（原 180-216 行）

【缺陷】
  原实现在 RLock 期间构造快照，但只把 map 的**引用**塞进去：
      s.mu.RLock()
      snap := snapshot{Nodes: s.nodes, Hosts: s.hosts, ...}  // ← 引用！
      s.mu.RUnlock()
      b, err := json.Marshal(&snap)                          // ← 解锁后才迭代 map

  json.Marshal 会迭代这些 map，而此时锁已释放，与写入路径直接撞车：
      · AddMetrics   → 写 s.hosts（Agent 每 30 秒上报，40 台即持续写入）
      · UpsertNode   → 写 s.nodes
      · SetSetting   → 写 s.settings
      · UpsertRule   → 写 s.rules

  Go runtime 检测到即抛 "fatal error: concurrent map iteration and map write"。
  这是 **fatal error 而非 panic，不可 recover**，整个进程直接死亡。

【为什么是 Blocker 而非 High】
  触发路径完全自动，无需任何异常操作：
      · StartAutoSave(60 * time.Second) → 每分钟快照一次
      · 40 节点 × 每 30 秒上报 = 平均每秒 1.3 次写入
  两者在时间上必然重叠。这不是"极端并发下的理论风险"，是**必然事件**。
  进程崩溃后 systemd 会 Restart=always 拉起，表现为"面板每隔几分钟闪断、
  数据回退到上次快照"，且日志里只有 Go 的 fatal 堆栈，很难归因。

  更糟的是：它此前从未被发现。首次部署验证只跑了几分钟、单节点、
  演示模式（-demo 下不发起真实探测），撞车窗口太小。
  **这类缺陷只有并发压测或代码审查能发现，功能测试发现不了。**

【证据】
  写了一个复现测试（40 节点 + 并发写 hosts/settings/rules + 连续 Save）：
      修复前：3 次运行 3 次崩溃，输出
        fatal error: concurrent map iteration and map write
        encoding/json.mapEncoder.encode(...)
        github.com/motao/probe/internal/store.(*Store).Save(...)
      修复后：300 次 Save 全部通过，无崩溃

【修复】
  持锁期间对全部快照字段做**深拷贝**，锁外再序列化：
      · Nodes/Services/Rules：解引用指针得到独立副本
      · Hosts/Settings：值类型，逐项复制
      · Alerts：逐条复制
      · Series/SvcRes：Ring.Slice() 本就返回副本
  锁内只做内存拷贝（微秒级），文件 I/O 与 JSON 编码留在锁外，
  不牺牲并发性能。

  附带收益：修复前若 marshal 期间数据被改，写出的快照可能是
  "半新半旧"的不一致状态；深拷贝后快照是一个时间点的原子视图。

【回归测试】internal/store/save_test.go
      TestSaveRacesWithWrites        并发 Save + 写入，300 轮不崩溃
      TestSavePersistsAllSections    深拷贝重构后 9 个字段无丢失，
                                     含令牌回填与"令牌不泄露到公开视图"
  已验证有效性：stash 掉修复后测试 FAIL，恢复后 PASS。


四、High：4 项
--------------------------------------------------------------------------------

【H1】CSV 公式注入 —— 打破了项目自己的核心安全承诺 ★最值得说的一项
  文件：internal/web/export.go  exportAssets / exportAlerts

  攻击路径（完整、可复现）：
      1. 攻击者攻破任意一台被监控机器的 probe-agent
      2. Agent 上报时自报 host.os = "=cmd|'/c calc'!A1"
         → handleReport 原样存入 s.hosts[nodeID]，无任何校验
      3. 管理员从设置页导出 assets.csv 查看台账
         → v.Host.OS 直接写入 CSV 单元格
      4. 管理员用 Excel/WPS 打开该 CSV
         → 单元格以 = 开头被当作公式求值，DDE 载荷执行系统命令

  为什么严重：项目的立身之本是"Agent 只读单向，攻击面从任意 RCE 降到
  只能伪造指标"。这条路径把攻击面从"伪造指标"提升回**"在管理员机器上
  执行命令"**，而且执行环境是管理员本人的桌面，权限高于任何被监控节点。
  承诺被绕过了，而绕过方式是"导出数据"这种日常操作。

  受影响的字段（均为 Agent 或管理 API 可控）：
      assets.csv: Name, Provider, Region, Group, Host.OS
      alerts.csv: RuleName, NodeName, Message
                  （Message 由 describe() 拼接 NodeName，间接可控）

  修复：新增 csvSafe()，对以 = + - @ Tab CR 开头的值加单引号前缀，
  Excel 会将其视为纯文本。不截断、不转义其余内容，正常数据零影响
  （"腾讯云-sg"、"Ubuntu 22.04"、"node-01" 原样保留）。

  回归测试：
      TestCSVSafeBlocksFormulaInjection   10 个用例（6 恶意 + 4 正常）
      TestAssetsExportEscapesHostOS       端到端：恶意 os 经真实导出后
                                          断言输出含 "'=cmd" 且不含 ",=cmd"

【H2】Content-Disposition 响应头注入
  文件：internal/web/export.go  sanitize()

  sanitize() 用于 metrics.csv 的文件名（取自 node.Name），
  原实现只替换文件系统非法字符 / \ : * ? " < > | 与空格，
  **未过滤 CR/LF 与控制字符**。

  node.Name 经管理 API 可控。若名称含 \r\n，
  拼进 Content-Disposition 后可注入额外响应头。

  修复：Replacer 补 \r \n 移除、\t 转 -，再用 strings.Map 清除
  全部 0x00–0x1F 与 0x7F。测试额外断言"任何输入的输出都不含 CR/LF"。

  回归测试：TestSanitizeStripsHeaderInjection（5 个用例）

【H3】停用告警规则后，其活跃告警永不恢复
  文件：internal/alert/alert.go  Evaluate()

  原实现对未启用的规则直接 continue：
      for _, rule := range rules {
          if !rule.Enabled { continue }   // ← 该规则的活跃告警再无人处理

  恢复逻辑（ResolveAlert）只在"规则启用且指标已回落"的分支里执行。
  规则一旦停用，它名下的活跃告警就失去了唯一的关闭路径，
  界面上永远挂着「进行中」，ActiveAlertCount 永不归零。

  这是 P3（规则界面编辑）引入的：在此之前规则不可停用，缺陷不存在。
  **新增能力打开了旧代码没考虑的状态转移** —— 典型的回归。

  修复：停用分支调用新增的 st.ResolveRuleAlerts(rule.ID)，
  并同步清理引擎的 active/since/lastAt。

【H4】删除节点不关闭其活跃告警 → 僵尸告警
  文件：internal/store/store.go  DeleteNode()

  原实现只删 nodes/series/hosts 三个 map，不碰 alerts。
  被删节点的活跃告警会永久挂在「进行中」，且因节点已不在 Nodes() 中，
  Evaluate 的恢复分支永远走不到它 —— 与 H3 同源，同样无法自愈。

  对比：DeleteRule 是有清理告警的。说明这是遗漏，不是设计取舍。

  修复：DeleteNode 一并把该节点的未恢复告警置为已恢复。

【H3+H4 的回归测试】internal/alert/alert_test.go
      TestDisabledRuleResolvesItsAlerts      停用后 ActiveAlertCount 归零，
                                             且引擎三个状态 map 均已清理
      TestDeletedRuleResolvesItsAlerts       删除规则同样不留僵尸告警
      TestEngineStateDoesNotLeakOnNodeDeletion
                                             20 轮"建节点→评估→删节点"，
                                             每轮断言告警关闭 + 状态无残留
  已验证有效性：stash 掉修复后 4 个测试全部 FAIL（含精确的
  "停用规则后活跃告警未关闭: got 1, 期望 0"），恢复后全部 PASS。

【M1】告警引擎状态 map 无限增长（内存泄漏）
  文件：internal/alert/alert.go

  since / active / lastAt 三个 map 的 key 是 "ruleID|nodeID"，
  只在"规则启用且节点存在"时才会被 delete。
  节点被删除或规则被停用后，其 key 再也不会被访问 → 永久残留。

  40 台机群反复换机、规则反复调整，条目只增不减。
  单条虽小，但这是长期运行的常驻服务，属于典型的慢性泄漏。

  修复：每轮评估记录实际访问到的 key 集合（seen），
  循环结束后清除三个 map 中不在 seen 里的条目。
  该修复同时是 H3/H4 的实现基础。

【M2】节点更新会静默轮换令牌，导致 Agent 立即 401
  文件：internal/web/web.go  handleAdminNodes POST 分支

  原实现无条件执行 in.Token = store.NewToken()。
  POST 带着已存在的 ID 更新台账（改名/改到期日/改价格）时，
  令牌被换成新值 → 该节点的 Agent 用旧令牌上报，立即开始 401。

  这与之前那个 json:"-" 令牌持久化 bug 是**同一类失效模式**：
  一次看似无害的管理操作，静默让节点失联。
  而且现象一样（Agent 刷 401），排查时会误以为是同一个 bug 复发。

  修复：区分三种情况
      · ID 为空           → 新节点，生成令牌
      · ID 已存在         → 更新，**保留原令牌**
      · ID 指定但不存在   → 视为新建，生成令牌
  需要轮换令牌应走显式流程，不该由一次台账更新触发。

  回归测试：TestNodeUpdatePreservesToken（断言令牌未变、台账字段已更新）
            TestNewNodeGetsToken（断言新节点仍生成 48 位令牌）
  已验证有效性：stash 掉修复后 FAIL（"令牌被轮换: got e46c07... 期望 original-token"）

【M3】lt 规则的告警文案说反
  文件：internal/alert/alert.go  describe()

  文案硬编码"超过阈值"，但规则的 op 可以是 lt。
  一条"可用率低于 99%"的规则触发时会显示"超过阈值 99%"，
  与事实相反。运维看到会误判方向。

  P3 引入了 op 可选 lt，但 describe() 没有同步 —— 又一处
  "新增能力未覆盖旧代码路径"的回归。

  修复：按 rule.Op 选择"超过"/"低于"。
  回归测试：TestDescribeRespectsOp（gt 不得含"低于"，lt 不得含"超过"）

【M4】deploy 模板与项目安全承诺矛盾

  直接照抄模板部署，管理面板就暴露在公网上：

六、Low：2 项 —— 安全验证方法本身是错的
--------------------------------------------------------------------------------

【L1】README 与注释里的验证指引必然"假通过" ★这条最容易被忽略
  文件：README.md 40-45 行、internal/collect/collect_linux.go 顶部注释、
        cmd/agent/main.go 顶部注释

  项目用两条命令来"证明"Agent 无法执行命令：
      grep -r "os/exec"    ./internal/collect/   # 声称：无输出
      grep -r "net.Listen" ./internal/collect/   # 声称：无输出

  两个问题：

  (a) **grep 源码必然命中注释本身**。
      collect_linux.go 的文档注释里就写着"不 import os/exec"、
      以及这两条 grep 命令自己。实测：
          grep -rn "os/exec|net.Listen" cmd/agent internal/collect
          → 4 处命中，全部是注释
      指引承诺"无输出"，实际有输出，且无法区分注释与真实调用。

  (b) **go tool nm 对剥离产物恒返回 0**。
      Makefile 用 -ldflags "-s -w" 构建，符号表被剥掉。此时
          go tool nm dist/probe-agent-linux-amd64 | grep -c ...
      会打印 "reading ...: no symbol section" 到 stderr，
      stdout 计数**恒为 0** —— 看起来"通过"，其实什么都没验证。
      我在审查中先踩了这个坑，看到 0 差点直接采信。

  如何确认结论仍然成立（这次是真的）：
      · go list -deps ./cmd/agent | grep -x 'os/exec'  → 无输出 ✔
        （依赖表由编译器生成，不受剥离影响，最可靠）
      · 用**未剥离**二进制验证符号表：
          nm 总符号数 8965（证明符号表在，grep 有效）
          os/exec | exec.Cmd        → 0
          net.Listen | TCPListener  → 0
      · **对照组**：server 二进制同样 grep → 9 个 Listen 符号
        有对照组才能证明 grep 模式本身是对的，而不是恒为 0。

  修复：三处注释与 README 全部改为上述正确方法，
  并显式写明两个陷阱（"不要 grep 源码"、"nm 必须用未剥离二进制"）
  和对照组要求。**验证方法写错比不写更危险** ——
  它给出虚假的信心，而这次虚假信心覆盖的正是项目最核心的安全承诺。

十一、遗留建议（未修改，属设计取舍，供决策）
--------------------------------------------------------------------------------
1. **探测目标可被用作 SSRF 探针**
   /api/admin/services 的 target 无地址白名单，管理员可让 server 去请求
   内网任意地址（如 http://169.254.169.254/ 取云厂商元数据）。
   但需要 X-Admin-Token，而持有令牌者本就等于管理员 → 属"管理员权限内"，
   不构成提权。若将来引入多用户/只读角色，此项需升级为 High。

2. **探测使用 InsecureSkipVerify: true**
   probe.go 跳过 TLS 校验，注释说明是"证书有效性单独评估"（通过 certDays
   字段单独反映），这个取舍合理。但代价是无法发现中间人攻击。
   若要收紧，可加一个 per-service 的 strictTLS 开关。

3. **告警规则不支持按节点/分组定向**
   所有规则对全部节点生效。40 台规模下"测试机磁盘 90%"和"生产机磁盘 90%"
   会触发同一条规则同等严重度。README 第八节已列为已知限制。

4. **通知投递无并发上限**
   applyNotifyConfig 里对每条告警 go notify.Send(...)，无信号量。
   若同时爆发大量告警（如整个机房断网，40 节点 × 4 规则 = 160 条）
   会瞬间起 160×通道数 个 goroutine 做外发 HTTP。
   单次 httpClient.Timeout 12s，量级可控但不优雅。
   建议加一个带缓冲 channel 做工作队列，限制并发投递数。

5. **快照无版本迁移机制**
   notify 配置有 v1→v2 迁移（Parse 里的 legacyConfig），
   但 snapshot 结构本身没有 version 字段。
   将来改 Store 结构时，旧 state.json 可能静默解析出零值。
   建议加 SavedSchemaVersion 并在 load() 里做迁移或显式拒绝。
